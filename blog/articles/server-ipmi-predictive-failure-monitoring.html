Категория: серверы

Предиктивная диагностика железа: мониторинг серверов YADRO и DEPO через IPMI

Отказ блока питания, остановка вентилятора или перегрев накопителя обычно оставляют аппаратные признаки до аварийного выключения сервера. Если контролировать эти признаки через BMC/IPMI, инженер сможет заменить компонент в согласованное окно, а не восстанавливать 1С, ERP и виртуальные машины после внезапного простоя.

Ниже — практическая схема для серверов YADRO и DEPO. Названия датчиков и возможности BMC зависят от модели, ревизии, дисковой корзины и версии прошивки, поэтому сначала нужно снять фактический перечень сенсоров конкретного сервера.

Что можно контролировать через IPMI

IPMI работает через отдельный контроллер управления BMC и продолжает собирать аппаратные события независимо от основной операционной системы. Это позволяет обнаруживать проблемы даже при зависании гипервизора или выключенном сервере, если на BMC подано дежурное питание.

Основные источники ранних предупреждений

Ограничение: IPMI показывает только датчики, которые BMC получает от платформы. Температура каждого диска и атрибуты SMART могут отсутствовать, особенно при использовании RAID-контроллера или корзины без передачи соответствующей телеметрии. В таком случае IPMI дополняют мониторингом SMART и RAID из операционной системы либо через штатную утилиту контроллера.

Пошаговая настройка диагностики

  1. Проверить BMC и обновить инвентарную карточку

    Зафиксируйте модель сервера, серийный номер, версию BMC, BIOS, RAID-контроллера и дисковой полки. Для YADRO и DEPO используйте документацию именно к установленной модели: одинаковое торговое семейство может содержать разные контроллеры управления.

    До обновления прошивок изучите примечания производителя, совместимость компонентов и порядок отката. Не обновляйте BMC, BIOS и RAID-контроллер одновременно на всех узлах кластера.

  2. Изолировать сеть управления

    Подключите BMC к отдельной административной сети или VLAN. Разрешите доступ только с сервера мониторинга и рабочих мест администраторов. Не публикуйте IPMI-интерфейс в интернете и не размещайте его в общей пользовательской сети.

    Создайте отдельную учётную запись мониторинга с минимальными правами на чтение датчиков. Не используйте заводской пароль, общую учётную запись администратора или один пароль для всего парка серверов.

  3. Снять перечень датчиков и журнал событий

    Установите ipmitool на защищённый сервер администрирования. Пароль лучше передавать через защищённый файл или хранилище секретов, а не указывать прямо в командной строке.

    export IPMI_PASSWORD_FILE=/secure/path/ipmi-password

ipmitool -I lanplus \
  -H bmc-server.example.local \
  -U monitoring \
  -f "$IPMI_PASSWORD_FILE" \
  sensor list

ipmitool -I lanplus \
  -H bmc-server.example.local \
  -U monitoring \
  -f "$IPMI_PASSWORD_FILE" \
  sdr elist all

ipmitool -I lanplus \
  -H bmc-server.example.local \
  -U monitoring \
  -f "$IPMI_PASSWORD_FILE" \
  sel elist

    Сохраните вывод для каждого сервера. Найдите датчики с названиями, относящимися к температуре дисков или корзины, блокам питания, резервированию питания, вентиляторам, памяти и общему состоянию системы. Не переносите названия сенсоров с другой модели без проверки.

  4. Подключить BMC к системе мониторинга

    Для централизованного контроля можно использовать Zabbix с IPMI-интерфейсом либо Prometheus с IPMI exporter. В обоих случаях опрос должен выполняться из изолированной сети управления под отдельной учётной записью.

    Для каждого сервера настройте сбор:

    • значений температурных датчиков;
    • оборотов и состояния вентиляторов;
    • статусов обоих блоков питания и резервирования;
    • состояния памяти и аппаратных ошибок;
    • доступности BMC;
    • новых записей System Event Log, если выбранная система поддерживает их обработку.

    Если используется Prometheus, BMC должен опрашивать exporter: передавать пароли от IPMI непосредственно серверу Prometheus нежелательно. В конфигурации экспортера укажите IPMI 2.0/LANPlus, минимально достаточный уровень привилегий и отдельный модуль для нужной группы серверов.

    modules:
  yadro_depo_readonly:
    user: monitoring
    pass: "получать_из_хранилища_секретов"
    privilege: user
    driver: LAN_2_0
    collectors:
      - bmc
      - ipmi
      - chassis

    Точный формат конфигурации проверьте по версии установленного экспортера. Секреты не следует хранить в репозитории, шаблоне виртуальной машины или открытом файле конфигурации.

  5. Создать правила уведомлений

    Не назначайте универсальную температуру для всех моделей. В первую очередь используйте штатные пороги Warning, Critical и Non-Recoverable, которые возвращает SDR. Дополнительный ранний порог задавайте только после изучения документации и нормальных значений конкретного сервера под рабочей нагрузкой.

    Разделите уведомления по срочности:

    • Предупреждение: температура приближается к штатному порогу, растёт несколько опросов подряд, появился корректируемый ECC или снизились обороты вентилятора.
    • Высокая важность: один БП отсутствует, потерял входное питание или нарушено резервирование, но сервер продолжает работать.
    • Авария: достигнут критический порог, отказал вентилятор, зарегистрирована некорректируемая ошибка памяти или аппаратный датчик перешёл в Critical.
    • Контроль мониторинга: BMC перестал отвечать, данные устарели или экспортер не может пройти аутентификацию.

    Чтобы исключить сообщения при кратком сетевом сбое, подтверждайте предупреждение несколькими последовательными опросами. Критическое дискретное событие — например отказ БП — обычно требует немедленного уведомления без длительного ожидания.

  6. Дополнить IPMI контролем дисков и RAID

    Если BMC не передаёт температуру накопителей, включите сбор данных внутри ОС. Для прямых дисков используют smartctl, для аппаратного RAID — поддерживаемую производителем утилиту контроллера. Контролируйте температуру, SMART-статус, ошибки носителя, состояние массива, наличие hot spare и ход восстановления.

    Команды просмотра должны соответствовать типу контроллера. Не запускайте принудительные тесты, очистку журнала, rebuild или изменение RAID на рабочем сервере без утверждённого регламента.

  7. Зафиксировать порядок реакции

    У каждого уведомления должны быть ответственный и действие. При потере одного БП инженер проверяет ввод питания, PDU, кабель и сам модуль; при перегреве дисковой зоны — температуру воздуха на входе, вентиляторы, фильтры, заглушки и размещение кабелей. Только после диагностики планируют замену компонента.

    Для кластера 1С или виртуализации заранее опишите перенос нагрузки, вывод узла в обслуживание, проверку резервных копий и возврат сервера в кластер.

Критерии проверки готовой системы

Мониторинг считается настроенным только после испытания полного пути от датчика до ответственного сотрудника.

  • BMC всех серверов доступен только из разрешённой административной сети.
  • Для мониторинга используется отдельная учётная запись с минимальными правами.
  • Система получает температуры, состояние вентиляторов, обоих БП и аппаратные статусы без постоянных ошибок опроса.
  • Контролируется потеря связи с BMC и устаревание последнего полученного значения.
  • Пороги сопоставлены со штатными значениями SDR и документацией конкретной модели.
  • Для дисков, не видимых через IPMI, подключены SMART или данные RAID-контроллера.
  • Тестовое событие доставляется в согласованный канал и содержит имя сервера, датчик, текущее состояние и время возникновения.
  • Повторяющиеся уведомления объединяются, но переход из Warning в Critical не теряется.
  • После восстановления состояния приходит отдельное сообщение, а инцидент закрывается только после проверки причины.
  • Для отказа БП, перегрева и деградации массива существует краткая инструкция действий.

Как безопасно провести проверку

Не отключайте блок питания и не останавливайте вентилятор на рабочем сервере ради теста. Сначала проверьте доставку на тестовом узле или воспользуйтесь предусмотренной производителем функцией генерации тестового события. Недоступность BMC можно проверить временным правилом на тестовом адресе либо контролируемой блокировкой доступа только для системы мониторинга.

После проверки сравните данные мониторинга с веб-интерфейсом BMC и текущим SEL. Значение, имя сенсора и статус должны соответствовать друг другу.

Типовые ошибки и краткий вывод

  • Доступ к IPMI из интернета. Интерфейс управления должен находиться в изолированной сети с ограничением источников доступа.
  • Мониторинг под администратором. Компрометация системы наблюдения в таком случае даёт лишние возможности управления сервером.
  • Одинаковые пороги для всего парка. Допустимые значения и расположение датчиков отличаются между моделями и конфигурациями.
  • Проверка только температуры CPU. Диски, память, вентиляторы и блоки питания могут деградировать без заметного роста температуры процессора.
  • Игнорирование резервирования. Сервер продолжает работать на одном БП, поэтому потеря второго модуля часто остаётся незамеченной до следующего отказа.
  • Отсутствие контроля свежести данных. График может выглядеть нормальным, хотя опрос BMC давно прекратился.
  • Очистка SEL без сохранения. Журнал содержит последовательность аппаратных событий, необходимую для поиска причины и обращения в поддержку.
  • Ожидание полной диагностики дисков через IPMI. При отсутствии нужной телеметрии необходим отдельный контроль SMART и RAID.
  • Уведомление без регламента. Само сообщение не предотвращает простой, если не определены ответственный, допустимое окно ремонта и порядок вывода узла.

Вывод: практическая предиктивная диагностика серверов YADRO и DEPO строится из трёх частей: безопасного доступа к BMC, регулярного сбора фактических датчиков и понятного порядка реакции. IPMI заранее показывает перегрев, потерю резервирования питания, проблемы вентиляторов и часть аппаратных ошибок. Там, где BMC не видит накопители или RAID, его дополняют мониторингом из операционной системы. Такая схема позволяет перенести нагрузку и заменить компонент в плановое окно, не дожидаясь аварийного отключения бизнес-критичного сервера.
