Категория: резервное копирование

Защита от «удаления админом»: диагностика режима Immutability в бэкапах «Киберпротекта»

Если злоумышленник получил права администратора домена, сервера резервного копирования или виртуальной инфраструктуры, обычные сетевые бэкапы уже нельзя считать защищёнными. Их можно удалить через консоль, повредить с помощью учетной записи хранилища или дождаться, пока политика ротации вытеснит последнюю пригодную копию. Поэтому наличие задания со статусом «Успешно» ещё не означает, что бизнес сможет восстановиться.

Практическая цель — вынести дополнительную копию в отдельное S3-совместимое хранилище, включить Object Lock, разделить административные роли и экспериментально подтвердить, что защищённые версии объектов нельзя удалить до окончания установленного срока. Отдельно нужно измерить фактический RPO: неизменяемость сохраняет уже записанные данные, но сама по себе не гарантирует своевременное создание копий.

Что именно должен защищать неизменяемый контур

S3 Object Lock блокирует изменение или удаление конкретных версий объектов на установленный срок. Для этого в корзине должно работать версионирование, а у записанных объектов должны присутствовать параметры удержания. Простое включение versioning не равно неизменяемости: пользователь может создать маркер удаления, удалить отдельную версию или изменить политику доступа, если хранилище это разрешает.

У Object Lock обычно применяются два режима:

  • Governance — удаление запрещено обычным пользователям, но субъект с правом обхода удержания может снять защиту или удалить версию.
  • Compliance — защищённую версию нельзя удалить до окончания срока штатными средствами S3, включая действия администратора корзины. Точная реализация и границы полномочий зависят от российского S3-провайдера, поэтому их необходимо подтвердить документацией и испытанием.

Для защиты от компрометации суперпользователя предпочтителен режим, при котором учётная запись Backup Gateway умеет записывать и читать данные, но не может сокращать retention, обходить Object Lock, удалять версии или менять политику корзины. Учётная запись управления S3 должна находиться в другом контуре и не использоваться на сервере «Кибер Бэкапа».

В типовой схеме «Кибер Бэкап» передаёт архив через Backup Gateway, входящий в состав «Кибер Инфраструктуры» или «Кибер Хранилища», а шлюз записывает данные во внешнюю S3-корзину. Локальная копия нужна для быстрого восстановления, неизменяемая удалённая — для переживания компрометации основной площадки.

Подготовка и настройка S3-хранилища

  1. Зафиксируйте модель угроз. Перечислите учетные записи, которые могут быть захвачены: администратор домена, администратор «Кибер Бэкапа», root на Backup Gateway, оператор виртуализации и пользователь S3. Проверка считается достаточной только тогда, когда компрометация каждой рабочей учетной записи не позволяет удалить последнюю пригодную копию.

  2. Выберите совместимое хранилище. Проверьте у поставщика поддержку S3 API, Signature Version 4, versioning, Object Lock, retention для отдельных версий, режима Compliance и журналирования операций. Совместимость с базовыми командами S3 не означает поддержку Object Lock.

  3. Создайте отдельную корзину. Не смешивайте бэкапы с прикладными объектами. Включите версионирование и Object Lock в порядке, который требует конкретный провайдер. У некоторых реализаций эти параметры необходимо задавать при создании корзины либо до первой загрузки данных.

  4. Задайте срок неизменяемости. Он должен перекрывать период, за который организация гарантированно обнаружит атаку, остановит заражение и выберет чистую точку восстановления. Срок нельзя выбирать только по расписанию ежедневной ротации. Учитывайте также жизненный цикл объектов: правило автоматического удаления не должно конфликтовать с retention.

  5. Разделите роли. Создайте техническую учетную запись для Backup Gateway с минимальным набором операций над нужной корзиной. Не выдавайте ей права управления пользователями, удаления корзины, изменения Object Lock, обхода Governance и сокращения срока удержания.

  6. Изолируйте управление. Включите многофакторную аутентификацию там, где её предоставляет оператор, храните аварийные реквизиты вне домена и ограничьте административный доступ отдельными рабочими местами, VPN или разрешёнными адресами.

  7. Подключите S3 через Backup Gateway. В «Кибер Хранилище» или «Кибер Инфраструктуре» создайте хранилище резервных копий, выберите внешний S3-сервис, укажите endpoint, регион, корзину и технические ключи. Для совместимого сервиса может потребоваться AuthV4 и адресация virtual-hosted-style либо path-style.

  8. Добавьте хранилище в «Кибер Бэкап». Зарегистрируйте узел хранения, назначьте его местом сохранения дополнительной копии и выполните полный цикл резервного копирования. Не переносите в защищённую корзину только метаданные: в ней должны появиться все объекты, необходимые для восстановления.

Перед включением в промышленную эксплуатацию согласуйте срок хранения с владельцем данных. В режиме Compliance ошибочно установленный длительный retention нельзя исправить обычным административным удалением, а занятое пространство останется недоступным для очистки до истечения срока.

Пошаговая диагностика Immutability и RPO

  1. Создайте контрольную копию. Выберите некритичную тестовую машину или набор файлов с известным содержимым. Запишите время изменения исходных данных, запуска задания, завершения копирования и появления архива в консоли.

  2. Проверьте объекты на стороне S3. Через консоль провайдера или совместимый клиент убедитесь, что у корзины включено версионирование, а у созданных версий объектов указаны режим блокировки и дата окончания retention. Статуса Object Lock у корзины недостаточно: защита должна быть применена к реально записанным версиям.

  3. Попробуйте удалить архив из «Кибер Бэкапа». Используйте только тестовый архив. После команды удаления проверьте не только исчезновение записи из интерфейса, но и состояние версий в S3. Интерфейс может удалить каталог или создать маркер удаления, тогда как защищённые версии сохранятся.

  4. Повторите удаление с ключами Backup Gateway. Попытайтесь удалить конкретную версию объекта и изменить её retention. Ожидаемый результат — отказ S3. Если техническая учётная запись может обойти удержание, модель защиты от компрометации шлюза не выполнена.

  5. Проверьте административный сценарий. В согласованном тестовом окне попробуйте удалить защищённую версию или сократить retention с учетной записью администратора корзины. Не используйте владельца всей облачной организации без заранее определённой модели угроз. Результат нужно сопоставить с заявленным режимом Governance или Compliance.

  6. Смоделируйте потерю управляющего сервера. Подготовьте чистый экземпляр поддерживаемой версии Backup Gateway и документированную процедуру повторного подключения существующих данных. Не выполняйте разрушительные действия в рабочем контуре. Цель испытания — убедиться, что сохранность объектов не зависит от единственного сервера управления.

  7. Выполните восстановление. Восстановите тестовые данные в изолированную сеть, проверьте открытие файлов, запуск системы и прикладную целостность. Успешное скачивание архива не подтверждает работоспособность приложения.

  8. Рассчитайте фактический RPO. Сравните время последнего изменения, попавшего в восстановленную систему, со временем инцидента или контрольной точки. Используйте результат реального восстановления, а не только расписание задания. Отдельно зафиксируйте RTO — время от решения о восстановлении до готовности системы к проверке пользователем.

  9. Настройте контроль. Отслеживайте пропущенные задания, возраст последней успешной копии, ошибки загрузки в S3, заполнение хранилища, изменение политик доступа и Object Lock, попытки удаления, срок действия ключей и сертификатов.

Критерии приёмки защищённого контура

Проверка Критерий успешности Подтверждение
Запись копии Задание завершено, необходимые объекты и версии появились в S3 Журнал «Кибер Бэкапа», журнал Backup Gateway и список объектов S3
Применение Object Lock У записанных версий указан требуемый режим и будущая дата окончания retention Метаданные нескольких объектов из разных архивов
Удаление оператором бэкапа Защищённые версии остаются в S3 Список версий до и после теста
Компрометация ключа шлюза Нельзя удалить версию, сократить retention или изменить настройки корзины Ответ S3 об отказе и событие в журнале аудита
Административное удаление Поведение соответствует выбранному режиму; в Compliance защищённая версия не удаляется до завершения retention Протокол испытания и журнал S3
Восстановление Данные восстановлены в изолированную среду и прошли прикладную проверку Акт тестового восстановления
RPO Фактическая потеря данных при тесте не превышает утверждённый бизнесом предел Временные метки исходных и восстановленных данных
Аудит Изменение политики и неуспешные попытки удаления видны ответственному сотруднику События журнала и тестовое уведомление

Результаты проверки храните отдельно от основной инфраструктуры: схема, перечень ролей, политики доступа, срок retention, журналы тестов, процедура повторного подключения и контакты ответственных. Если эта документация доступна только в скомпрометированном домене, в момент атаки она может оказаться недоступной.

Типовые ошибки и краткий вывод

  • Путать versioning с Object Lock. Версионирование помогает вернуть предыдущую версию, но без удержания пользователь с достаточными правами может удалить её окончательно.
  • Включить Object Lock только на уровне корзины. Проверять нужно retention у конкретных объектов, созданных Backup Gateway.
  • Использовать Governance без ограничения обхода. Если рабочему ключу доступна операция обхода, защита от захваченного администратора становится условной.
  • Хранить S3-ключи администратора на сервере бэкапов. Компрометация одной системы тогда открывает и управляющий, и защищаемый контур.
  • Разрешить технической учётной записи менять политику корзины. Для штатной записи резервных копий административные полномочия обычно не нужны.
  • Считать удаление из консоли доказательством уничтожения данных. В S3 мог появиться только маркер удаления, а защищённые версии остались доступными для восстановления.
  • Выбирать retention короче времени обнаружения атаки. К моменту расследования злоумышленник может дождаться окончания блокировки.
  • Считать расписание подтверждением RPO. Задание может запускаться вовремя, но не завершать передачу в удалённое хранилище.
  • Не проводить полное восстановление. Целый объект или архив ещё не гарантирует загрузку операционной системы и согласованность приложения.
  • Делать S3 единственной копией. Недоступность канала или провайдера увеличит время восстановления; локальная оперативная копия решает другую задачу и должна сохраняться.

Защищённый бэкап-контур строится не одной настройкой Immutability. Нужны отдельная S3-корзина, Object Lock на версиях объектов, минимальные права Backup Gateway, независимое администрирование и регулярный тест восстановления. Контур можно считать принятым только после попытки удаления рабочими и административными учётными записями, проверки журналов и измерения фактического RPO на восстановленных данных.

При проектировании сверяйте команды и доступные режимы с документацией установленной версии «Кибер Бэкапа», «Кибер Хранилища» и выбранного S3-провайдера. Полезные первичные материалы: подключение внешнего S3 через Backup Gateway и описание Object Lock и сценариев восстановления.
